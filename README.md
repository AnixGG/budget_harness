# Budget Harness

Агент на openJiuwen для решения задач при общем лимите токенов. Поддерживает
математику, поиск по локальным файлам, CSV и исправление Python-кода.
Планировщик выбирает задачи и модель по ожидаемым баллам и расходу, затем
пересчитывает план после каждой попытки с учётом фактического расхода API.

## Сборка и запуск

Нужен Docker. На машине проверяющих используется Linux x86_64.

```bash
git clone https://github.com/AnixGG/budget_harness.git
cd budget_harness
docker build --platform linux/amd64 -t budget-harness:1.0.0 .
```

Задайте `LLM_BASE_URL` и `LLM_API_KEY` в окружении. Адрес должен быть полным
HTTPS URL совместимого API, включая `/v1`, если он требуется прокси.
`TASKS` на хосте — абсолютный путь к каталогу задач. Запуск по схеме организаторов:

```bash
export TASKS=/absolute/path/to/tasks
export BUDGET=100000

timeout -k 1000s 1h docker run --rm \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  budget-harness:1.0.0 \
  /app/run_agent.py --tasks-dir /data/tasks
```

`hack-net` предоставляет окружение проверки; это сеть с доступом к прокси.
Для собственного запуска выберите имеющуюся сеть с таким доступом.
`timeout` в примере — команда Linux. На macOS можно использовать `gtimeout`
из GNU coreutils; сам агент ограничивает работу 3500 секундами.
Без переопределения `--entrypoint` образ тоже запускает `run_agent.py`.

## Вход и результат

```text
tasks/
  math_0000/
    task.json
    answer.txt          # появляется после решения
  coding_0001/
    task.json
    workspace/          # исходники и предоставленные тесты
    answer.txt
```

`task.json` содержит `task_id`, `task_type`, `instruction`, `reward`.
Типы: `math`, `search`, `data_analysis`, `coding`. Файлы задачи лежат в
`workspace/`. Поля `expected` и `check` из учебных примеров не передаются модели.

Ответ записывается в `answer.txt` **рядом с `task.json`** сразу после решения.
Для coding сохраняются изменения исходников и `DONE` после прохождения
неизменённых публичных тестов. Для остальных типов сохраняется значение ответа.
При пропуске файл не создаётся. Уже существующий `answer.txt` не перезаписывается.
Прохождение публичных тестов не гарантирует прохождения скрытых.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `LLM_BASE_URL` | HTTPS адрес прокси | обязательна для API |
| `LLM_API_KEY` | ключ прокси | обязательна для API |
| `BUDGET` | общий бюджет: входные токены / 10 + выходные | `100000` |
| `TASKS` | путь к задачам **в контейнере** | нужен, если нет `--tasks-dir` |
| `OUT` | необязательный JSON-файл со статусами попыток | не создаётся |
| `HARNESS_REQUESTS_PER_MINUTE` | предел частоты запросов | `60` |
| `HARNESS_RATE_LIMIT_STATE` | файл состояния ограничения частоты | `/tmp/jiuwen-api-rate-limit.json` |

Аргументы `--tasks-dir`, `--budget`, `--out` имеют приоритет над соответствующими
переменными. Переменные хоста попадают в контейнер только через `-e` или
`--env-file`; `.env` автоматически не читается.

В примере запуска из регламента `OUT` и `BUDGET` не передаются. Этот вариант
поддержан: ответы сохраняются в каталогах задач, бюджет равен 100000.
Если нужен дополнительный JSON, добавьте перед именем образа
`-e OUT=/data/tasks/solutions.json`. Он обновляется после каждой завершённой
попытки и содержит статусы и расход; сами ответы остаются в `answer.txt`.
`OUT` должен указывать на файл в доступном для записи каталоге, а не на каталог.

Логи и журнал расхода по умолчанию лежат в `/tmp/jiuwen-runs` и исчезают при
удалении контейнера. Для сохранения добавьте после аргументов агента
`--artifacts /data/tasks/run-logs`. Для каждого запуска нужен новый каталог логов.
Повторный запуск не восстанавливает расход предыдущего: оставшийся бюджет
следует передать отдельно после сверки журнала с провайдером.

## Как устроено решение

Для каждой задачи рассматриваются четыре плана — по одному на разрешённую
модель: `qwen3.8-27b`, `qwen3.8-27b-noreason`, `qwen3.6-35b-a3b`,
`qwen3.6-35b-a3b-noreason`. Расход оценивается по медианам собранных траекторий,
вероятность успеха — по долям успешных решений для типа задачи и плана.
Эти таблицы зафиксированы в `configs/`; обучения при запуске нет.

Планировщик решает задачу множественного выбора с ограничением бюджета:
максимизирует сумму `reward × p_success`, выбирая не более одного плана на задачу.
После выполнения одной задачи он пересчитывает выбор. По умолчанию оставляет
10% бюджета вне плановой оценки и отдельно проверяет запас для каждого запроса.

Модель возвращает JSON-действие: выполнить Python, сдать ответ или пропустить
задачу. Python работает в каталоге задачи. Для вариантов `noreason` требуется
одно законченное действие; для reasoning разрешено несколько шагов.
Сдача через `submit_answer(value)` или запись `answer.txt` завершает попытку
без дополнительного обращения к модели.

Каждый физический запрос, включая повторы, учитывается отдельно по `usage` API.
Reasoning-токены входят в выходные; скидки за кеш нет. Если расход запроса
неизвестен, следующие запросы прекращаются. Лимиты по умолчанию: 100 задач,
400 запросов и 3500 секунд. Выполнение последовательное, одна сессия.

Отдельный классификатор невыполнимости в релизе отключён: решение о пропуске
принимает агент по доступным данным. Локальных языковых моделей, энкодеров и
скачивания весов нет. Все зависимости устанавливаются при сборке.

## Проверка и история

Версия 1.0.0 содержит проверенный RC1 без экспериментальных изменений промптов.
Для выбора оценщиков собрано 384 наблюдения на 96 синтетических задачах
(48 семейств, четыре модели); разделение на обучение и валидацию сделано по
семействам. В релиз включены итоговые таблицы, без датасетов и сырых траекторий.

На локальном наборе из 80 задач текущая версия решила 66 из 68 выполнимых,
набрала 204 из 211 доступных баллов и потратила 48310.1 единицы бюджета.
Это один синтетический прогон, не результат на закрытом наборе организаторов.
Эксперименты с сокращёнными промптами, дополнительными инструментами и
нейросетевыми оценщиками сохранены отдельно от релизного репозитория.

Для этого кода пройдены 15 проверок контейнера с подставными ответами API:
сдача ответа, coding, повторы, лимиты, отмена и неизвестный расход.
Проверен образ `linux/amd64` под эмуляцией на ARM64 с read-only корнем и
отключённой сетью. Нативное время работы на Xeon не измерено.

Проверка соответствия кода зафиксированной конфигурации без обращения к API:

```bash
docker run --rm --network none --read-only --tmpfs /tmp:rw,size=2g \
  --entrypoint python budget-harness:1.0.0 -m harness.bundle check
```

Python 3.13.11 и зависимости зафиксированы; установка проверяет хеши из
`requirements*.lock`. Изменение рабочих модулей или промптов требует повторной
проверки совместимости таблиц: при несовпадении релиз останавливается до вызова API.
